# Refatoração modular do backend e centralização da camada HTTP do frontend

A refatoração separa o bootstrap do Express das rotas, controllers, services, validadores e tratamento de erros, preservando os endpoints e os payloads válidos. No cliente, a comunicação HTTP foi centralizada e o estado do dashboard foi extraído para um hook; o fixer também passou a mostrar falhas de adicionar/remover lançamentos. Os testes nativos do servidor e cliente, os builds isolado e raiz e o smoke test de importação do Express passaram. **Watch for:** **confirmed** o middleware de erro responde 500 para JSON malformado; **confirmed** o refresh do dashboard engole falhas depois de uma criação, deixando a UI potencialmente desatualizada; **confirmed** fallback de JWT, `localStorage` e CORS aberto continuam deliberadamente adiados pelo plano.

**Verdict**: NEEDS_CHANGES

## High-level view

O backend agora pode ser montado sem `listen` e organiza a API por domínio, com validação e respostas de erro centralizadas. A separação preserva os caminhos, autenticação Bearer, respostas válidas e o serving do cliente, mas o novo error handler ainda classifica uma entrada JSON sintaticamente inválida como erro interno.

A camada HTTP e o hook do dashboard removem `fetch` duplicado e o fixer cobre as rejeições diretas de criação e remoção na tela. Como o hook captura falhas no refresh antes de devolvê-las, uma criação que persiste no servidor pode limpar o formulário sem atualizar a lista nem informar que a sincronização falhou.

O teste de parcelamento e os testes de integração leve da camada frontend passaram, e não houve alteração de Render, Docker, Compose ou CI. A postura de segurança da sessão permanece a anterior por decisão explícita do plano e precisa ser tratada separadamente antes de aumentar a exposição ou a sensibilidade dos dados.

### Bootstrap Express e contratos da API

A montagem foi deslocada para `C:/caderneta-off/financas/caderneta-app/server/src/app.js`, enquanto `C:/caderneta-off/financas/caderneta-app/server/src/index.js` ficou restrito a configuração, conexão e `listen`. Os routers preservam `POST /api/auth/send-code`, registro, login, `/me`, transações e orçamentos; os controllers continuam delegando a services e o filtro por `req.userId` permanece nos acessos de recursos. O smoke test confirmou que o app é importável sem abrir uma porta.

A validação explícita mantém respostas válidas e rejeita tipos, datas, categorias e parcelas inválidos antes da persistência. O problema **confirmed** está no limite da nova camada de erro: `express.json()` pode produzir um erro com `type` `entity.parse.failed`, mas `C:/caderneta-off/financas/caderneta-app/server/src/middleware/errorHandler.js` só trata `AppError`, erros Mongoose e duplicidade. Um corpo JSON truncado ou inválido, portanto, recebe `{ error: 'Erro interno do servidor' }` com HTTP 500, embora seja uma entrada inválida que deveria seguir o contrato uniforme de 400.

### Parcelamento mensal e validação de domínio

`calculateInstallments` foi extraída como função pura e conserva a descrição numerada, o arredondamento e o ajuste para o último dia de fevereiro e outros meses curtos. `npm test --prefix C:/caderneta-off/financas/caderneta-app/server` e `node --test C:/caderneta-off/financas/caderneta-app/server/test/transactionService.test.js` passaram com os dois casos representativos.

A cobertura ainda é focada na função pura: não verifica em runtime cada contrato HTTP, isolamento por usuário, respostas do error handler ou criação parcial quando uma parcela falha, deixando as bordas da nova decomposição sem proteção de integração.

### Camada HTTP e sincronização do dashboard

`C:/caderneta-off/financas/caderneta-app/client/src/services/api.js` concentra JSON, Bearer e conversão de respostas não-2xx. `AuthContext` preserva `caderneta_token` e `caderneta_user`, `AuthPage` envia o código de registro e `DashboardPage` agora captura falhas diretas de criar/remover e apresenta uma mensagem. Os três testes de `C:/caderneta-off/financas/caderneta-app/client/test/frontendMigration.test.js` passaram.

Há um caminho de falha **confirmed** ainda aberto em `C:/caderneta-off/financas/caderneta-app/client/src/hooks/useDashboardData.js`: `refresh()` envolve as duas consultas em `Promise.all`, captura qualquer rejeição e apenas chama `console.error`. `addTransaction()` aguarda essa função depois de uma criação bem-sucedida; se a consulta seguinte falhar por expiração do token, rede ou erro 5xx, o refresh resolve como sucesso, `DashboardPage` limpa o formulário e a lista permanece antiga sem feedback. O mesmo catch também torna falhas do carregamento inicial invisíveis para a UI. A correção deve preservar o tratamento já adicionado na página, fazendo o hook propagar a falha ou expondo um estado de erro/sincronização.

### Postura de sessão, trust boundary e integração externa

A postura de segurança é **confirmed** deliberadamente mantida pelo plano: `C:/caderneta-off/financas/caderneta-app/server/src/config/env.js` aceita `caderneta-chave-secreta-2026` quando `JWT_SECRET` não existe; `C:/caderneta-off/financas/caderneta-app/client/src/context/AuthContext.jsx` persiste o JWT em `localStorage`; e `C:/caderneta-off/financas/caderneta-app/server/src/app.js` continua usando `cors()` sem allowlist. O envio para Brevo também permanece sem timeout. Essas escolhas não são regressões do refactor e estão registradas como pendências, mas mantêm riscos de tomada de sessão, origem cross-site e indisponibilidade do cadastro; devem ser endurecidas antes de ampliar usuários ou dados sensíveis.

Passaram `npm test --prefix C:/caderneta-off/financas/caderneta-app/server`, o teste direto de parcelamento, `npm test --prefix C:/caderneta-off/financas/caderneta-app/client`, `npm run build --prefix C:/caderneta-off/financas/caderneta-app/client` e `npm run build --prefix C:/caderneta-off/financas/caderneta-app`.
